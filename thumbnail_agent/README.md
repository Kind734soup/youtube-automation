# Thumbnail Agent

Turns a project's script and scene plan into 3 ranked YouTube thumbnail
concepts and one polished, ready-to-use image-generation prompt for the
strongest one. It is a completely separate agent from the Research
Agent (`agent/`), Script Agent (`script_agent/`), Video Production Agent
(`video_production_agent/`), Voice Generation Agent
(`voice_generation_agent/`), Video Editor Agent (`video_editor_agent/`),
FFmpeg Render Agent (`ffmpeg_render_agent/`), Visual Generation Agent
(`visual_generation_agent/`), and Publishing Agent (`publishing_agent/`)
- it does not import from any of them, and does not modify anything
they produce.

**This agent does not call any paid image-generation API and does not
produce `thumbnail.png` itself.** For Version 1 it only runs a free
`ManualProvider` for the *text* concept-writing step (paste a prompt
into Claude Pro yourself, no API cost or key needed) and writes the
concepts plus a polished prompt for a human (or a future image
provider) to act on. Wiring up a real image provider is future work -
see "Future provider integration" below.

## What it consumes

Three files from a Script Agent output folder (`scripts/<topic-slug>_<date>/`),
plus one optional folder:

- `metadata.json` (required) - the video's `topic`
- `script.md` (required) - only its opening excerpt is used (first ~1200
  characters, headings stripped), to capture the story's mood/setting
  without sending the entire multi-thousand-word script through a
  prompt
- `production_manifest.json` (required) - every scene's `scene_number`,
  `title`, and `visual_prompt`, used as the visual context for concept
  design
- `assets/visuals/scene_NN.png` (optional) - if the Visual Generation
  Agent has already run, these filenames (never the image bytes
  themselves) are listed in the prompt so concepts can stay visually
  consistent with the scenes already generated

It never modifies `narration_manifest.json`, `edit_manifest.json`, or
any video/audio asset.

## What it produces

Two files, written into the project's `final/<topic-slug>_<date>/`
folder - the same folder the FFmpeg Render Agent and Publishing Agent
already use, since a thumbnail prompt only makes sense paired with the
video it's for, and this is exactly where `thumbnail.png` itself will
eventually live:

- `thumbnail_prompt.md` - human-readable: all 3 concepts in full detail,
  ranked, the recommended one marked, and the final polished
  image-generation prompt in a copy-pasteable code block
- `thumbnail_manifest.json` - machine-readable, with a `thumbnail_path`
  field (`final/<topic-slug>_<date>/thumbnail.png`, relative to the
  repo root) and `thumbnail_exists` flag computed the same way the
  Publishing Agent computes them - see "Publishing Agent compatibility"
  below

Neither file is itself the thumbnail image. Once an image (from either
provider is connected later, or generated by hand from
`final_image_prompt`) is saved to that same `final/<topic-slug>_<date>/thumbnail.png`
path, the Publishing Agent (unmodified) picks it up automatically.

## How it works

1. **`manifest_reader.py`** - pure parsing, no AI. Reads `metadata.json`,
   the `script.md` excerpt, `production_manifest.json`'s scenes, and
   lists any existing `assets/visuals/scene_NN.png` filenames.
2. **`thumbnail_writer.py`** - builds the system/user prompt asking for 3
   ranked concepts (main subject, background, composition, lighting,
   colors, focal emotion, ≤4-word text overlay, and what to avoid, per
   concept) plus a recommended pick and a polished final prompt; calls
   `llm_client.py`; parses the reply as JSON and validates it (exactly 3
   concepts, all required fields present, soft warnings for anything
   like an over-length text overlay).
3. **`llm_client.py`** / **`llm_providers/`** - provider-agnostic AI text
   generation, the same split `script_agent` uses. `LLMProvider` is the
   interface (`llm_providers/base.py`); `manual_provider.py` is the only
   one wired up today.
4. **`organizer.py`** - reads the inputs, calls `thumbnail_writer.py`,
   and writes `thumbnail_prompt.md` + `thumbnail_manifest.json` into the
   matching `final/` folder.
5. **`main.py`** - CLI wrapper.

## Usage

```
python thumbnail_agent/main.py generate --from-script scripts/<topic-slug>_<date>
python thumbnail_agent/main.py generate --from-script scripts/<topic-slug>_<date> --force
python thumbnail_agent/main.py generate --from-script scripts/<topic-slug>_<date> --provider manual
```

- `generate` builds `thumbnail_prompt.md` and `thumbnail_manifest.json`.
  If `thumbnail_manifest.json` already exists, it's left alone and
  reported as skipped - pass `--force` to rebuild it anyway (matching
  the same idempotency convention as every other agent in this
  project).
- `--provider` selects a thumbnail LLM provider by name (default:
  `THUMBNAIL_LLM_PROVIDER` in `.env`, or `manual` if unset). This is a
  deliberately separate setting from `script_agent`'s `LLM_PROVIDER` -
  the two agents run independently.

## The `ManualProvider`

Free, no API key, no billing. Running `generate` with it:

1. Builds the concept-writing prompt and saves it to
   `thumbnail_agent/_manual_prompts/prompt_NN.txt` (this agent's own
   folder - it never touches `script_agent`'s `scripts/_manual_prompts/`).
2. Prints the prompt for you to paste into Claude Pro yourself.
3. Waits for you to paste Claude's full JSON reply, terminated by a line
   containing only `END`.
4. Parses and validates the reply, then writes both output files.

## Publishing Agent compatibility

The Publishing Agent doesn't read `thumbnail_manifest.json` at all - it
only checks whether `final/<topic-slug>_<date>/thumbnail.png` exists.
`thumbnail_manifest.json`'s own `thumbnail_path` field is computed with
the exact same convention (`final/<folder-name>/thumbnail.png`, relative
to the repo root), so once a real `thumbnail.png` is dropped into that
folder, both agents agree on where it lives, and the Publishing Agent's
`prepare` (rerun with `--force`) will report `thumbnail_exists: true`
and its `publish` checklist will stop warning about a missing
thumbnail - confirmed below under "Tested against".

## Future provider integration

`thumbnail_agent/llm_providers/` already has the same provider seam
`script_agent` uses - to add a live text provider later (e.g. a direct
Anthropic API call instead of manual paste):

1. Write `thumbnail_agent/llm_providers/<name>_provider.py` implementing
   `LLMProvider` (see `llm_providers/base.py`).
2. Add one line to `get_provider()` in `llm_providers/__init__.py`.
3. Set `THUMBNAIL_LLM_PROVIDER=<name>` in `.env`.

A future *image*-generation provider (the actual `thumbnail.png` pixels)
is a separate, not-yet-built integration: it would consume
`thumbnail_manifest.json`'s `final_image_prompt` field and write its
output straight to `thumbnail_path` - no other file in this agent would
need to change.

## Setup

No system dependencies for the agent itself (the `ffmpeg`-generated test
thumbnail described below was only for verifying Publishing Agent
compatibility, not something this agent needs day-to-day). Only pip
package is `python-dotenv`, already used project-wide for `.env`.

## Tested against

Ran against the existing Nightfall Atlas Ancient Egypt project
(`scripts/fall-asleep-to-the-entire-story-of-ancient-egypt-pyramids-pharaohs-and-gods-ancient-history_2026-08-01/`,
which already had all 8 scene reference images in `assets/visuals/` from
the Visual Generation Agent):

- `generate` (manual provider) produced 3 distinct concepts - "Giza
  Under the Stars" (pyramids at night with a small sleeping silhouette),
  "The Golden Barque of Ra" (the god Ra glowing on his barque), and
  "River of the Pharaohs" (a lantern-lit reed boat) - each with all 8
  required fields, a 4-word-or-fewer text overlay, and a specific
  "avoid" note; ranked 1-2-3; recommended concept 1 with a stated
  reason; and a full polished `final_image_prompt`. Both
  `thumbnail_prompt.md` and `thumbnail_manifest.json` were written to
  `final/<slug>_<date>/`, with `thumbnail_path` set to
  `final/<slug>_<date>/thumbnail.png` and `thumbnail_exists: false`
  (no warnings).
- Re-ran `generate` with no `--force`: correctly skipped instead of
  rewriting.
- Generated a placeholder `thumbnail.png` with `ffmpeg` directly into
  `final/<slug>_<date>/` (same technique the Publishing Agent's own
  README used to test itself) and ran the unmodified Publishing Agent's
  `prepare --force`: `Thumbnail:` flipped from `(not found yet)` to
  `(found)`. Ran `publish`: no warnings, status
  `ready_for_manual_upload`, `Thumbnail:` line showed the same path this
  agent recorded. Removed the test thumbnail afterward and rebuilt
  `upload_manifest.json` so the repo reflects the project's real state
  (no thumbnail yet) - `thumbnail_prompt.md` and `thumbnail_manifest.json`
  themselves were left in place as real output.
- Confirmed bad LLM replies are rejected clearly: a JSON reply with only
  2 concepts raises `ValueError: Expected exactly 3 thumbnail concepts,
  got 2`; a concept missing a required field raises `ValueError`
  naming the concept and the missing field(s); a non-JSON reply raises
  a `ValueError` quoting where parsing failed.

## Out of scope

No image-generation provider is connected yet - this agent only ever
produces text (`thumbnail_prompt.md`, `thumbnail_manifest.json`), never
`thumbnail.png` itself. It does not call the YouTube API, does not
touch `upload_manifest.json`, and does not manage playlists or
publishing - all of that remains the Publishing Agent's job.
